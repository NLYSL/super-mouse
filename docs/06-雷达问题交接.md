## 2. 协议（已验证，来自官方文档）

依据《**LD2454 串口通信协议 V1.00**》（2026-05-13）。

获取方式（官网文档列表是 JS 动态加载的，直接抓页面拿不到）：

```bash
curl -sL -X POST \
  -H "X-Requested-With: XMLHttpRequest" \
  -H "Content-Type: application/x-www-form-urlencoded; charset=UTF-8" \
  -H "Referer: https://h.hlktech.com/Mobile/download/FDetail/415.html" \
  --data "id=415" \
  "https://h.hlktech.com/Mobile/Download/queryResouceInfo"
```

返回 JSON 里的 `resource_url` 就是 PDF 直链（**路径含中文和空格，要 URL 编码**）。

### 2.1 接口 J1

| Pin | 信号 | 接到 XIAO |
|---|---|---|
| 1 | **5V** | 5V |
| 2 | GND | GND |
| 3 | TX（雷达发） | D7 = GPIO17 |
| 4 | RX（雷达收） | D6 = GPIO16 |

**LD2454 没有 OUT 引脚。** 只有这 4 根。模块出厂**不带排针**（5 个孔，孔径 0.8mm、间距 2.0mm，需自己焊）。

### 2.2 串口参数

**256000 波特率，8 数据位，1 停止位，无校验。**

其他可选波特率（协议 §2.2.6 表6）：115200 / 230400 / 460800 / 57600 / 38400 / 19200 / 9600。

### 2.3 目标数据帧（30 字节，10 帧/秒）

```
AA FF 03 00 | 目标1(8B) | 目标2(8B) | 目标3(8B) | 55 CC
```

每个目标 8 字节，全部**小端**：

| 偏移 | 字段 | 单位 |
|---|---|---|
| 0–1 | X 坐标 | mm |
| 2–3 | Y 坐标 | mm |
| 4–5 | 速度 | cm/s |
| 6–7 | 距离分辨率 | mm |

**符号约定特殊**：最高位为 **1 表示正数**，为 **0 表示负数**，数值取低 15 位。
全零的 8 字节 = 该目标槽位为空。

文档 §2.3 的示例帧：

```
AA FF 03 00  0E 03 B1 86 10 00 40 01  00×8  00×8  55 CC
→ 目标1: x=-782mm  y=1713mm  speed=-16cm/s  分辨率=320mm
```

**已验证**：项目里现成的 `LD2450Parser` 逐字节解对了这个示例帧。帧格式不用重写。

### 2.4 多目标模式（关键）

**出厂默认是「单目标追踪」**（协议 §2.2.5）。默认模式下雷达只报一个目标，
**永远检测不到"第二个人"** —— 这直接决定项目核心需求能否实现。

必须通过 Pin4 RX 下发命令切换。命令帧结构：`FD FC FB FA | 长度(2,LE) | 值 | 04 03 02 01`

```
使能配置   FD FC FB FA 04 00 FF 00 01 00 04 03 02 01
切多目标   FD FC FB FA 02 00 90 00 04 03 02 01
结束配置   FD FC FB FA 02 00 FE 00 04 03 02 01
```

规则（协议 §2.2.1）：**任何命令前必须先"使能配置"，配完必须"结束配置"**恢复工作模式。
ACK 帧的命令字 = 请求命令字 `| 0x0100`，其后 2 字节状态 `00 00` 表示成功。

固件已实现这套流程（`enableMultiTarget()`），但**没验证过**（雷达没出数据，ACK 收不到）。

## 4. 当前阻塞：雷达不发数据

固件的引脚电平诊断结果（`!level` 命令，或开机扫描失败后自动打印）：

```
D7  GPIO17 : 被驱动 · 恒高      ← Pin3 TX 接通了
其余 10 脚 : 全部悬空
所有波特率 : 零字节
```

**判读**：空闲的 UART TX 线就是恒定高电平。所以 TX 物理连通，但**雷达一个字节都没发**。

诊断原理：分别用内部下拉、上拉读同一个脚 —— 悬空脚会跟着内部拉走（两次读数相反），
被外部驱动的脚不会（两次一致）。

### 待办（需要人动手，不是软件问题）

1. **Pin1 接 5V**（推断，但依据明确）—— 协议 §1 要求 5V。此前一直按 3.3V 接，
   因为看的是**错误型号 LD2401 的数据手册**（那份写 3.3V）。用户反馈雷达指示灯
   "时亮时不亮、重插就亮" —— 供电不足的典型症状。**这是当前最可能的原因。**
2. **Pin4 RX 接到 D6/GPIO16** —— 现在悬空。不接就无法下发多目标命令，
   核心需求实现不了。

接好后验证：

```bash
python tools/radar_probe.py --scan
```

期望看到 `AA FF 03 00` 帧头、约 10 帧/秒、`#MULTI 已启用多目标追踪`。

**如果接 5V 后仍然零字节**，再查：模块是否焊接虚接（出厂无排针）、
是否 TX/RX 接反、模块本身是否损坏（可用 USB-TTL 直连雷达绕开 XIAO 验证）。

## 5. 已经踩过的坑（别重复）

### 5.1 pyserial 的 DTR 会复位 ESP32-C6 ★

**ESP32-C6 的原生 USB CDC 把 DTR 当复位线**，而 pyserial 打开端口时默认置位 DTR
→ 芯片被按在复位状态 → **端口能打开但读到 0 字节**。

这个现象一度被误判为"板子烧了"。正确写法：

```python
ser = serial.Serial()
ser.port = "/dev/cu.usbmodem1301"
ser.baudrate = 115200
ser.dtr = False      # 必须在 open() 之前
ser.rts = False
ser.open()
```

`serial_client.py` 里已经这么处理了。写任何新的调试脚本都要注意。

### 5.2 型号搞错会让整个排查方向偏掉 ★

前期一直用 **LD2401** 的数据手册排查（用户最初说 LD2404，后更正为 LD2454）。
LD2401 有 OUT 引脚（高低电平报有人/无人），于是花了很多时间在 OUT 引脚方向上，
还把 D7 的恒高电平误读成"OUT 报告有人"。

实际上 **LD2454 没有 OUT 引脚**，那个恒高就是空闲的 TX 线。
**只认《LD2454 串口通信协议 V1.00》，别用其他型号的文档类推。**

### 5.3 扫描输入引脚时不能指定 TX

固件扫描候选引脚时若给 `Serial1.begin()` 传了 TX 引脚，而雷达的 TX 正好接在那儿，
ESP32 的推挽输出会和雷达的输出驱动器对顶，**可能烧掉任一侧**。
只读时一律传 `tx = -1`。固件里已全部改好。

### 5.4 固件扫描期间不响应命令

开机扫描要跑 11 引脚 × 8 波特率约 18 秒，期间固件不处理 `!level` 等命令。
要么等它跑完，要么用 RTS 复位后从头听：

```python
ser.rts = True;  time.sleep(0.15)
ser.rts = False; time.sleep(0.1)
```

### 5.5 flash 可能丢固件

曾出现 `no bootable app partitions in the partition table` + 反复重启 —— flash 里没有
可运行程序，芯片在 ROM 引导里打转，表现也是串口静默。用 esptool 读 chip_id 可确认芯片存活：

```bash
~/Library/Arduino15/packages/esp32/tools/esptool_py/*/esptool \
  --port /dev/cu.usbmodem1301 --chip esp32c6 chip_id
```

## 6. 待实现：「第二个人」判定

`supermouse/modes/strong_sense/presence.py` 现在按**距离 + 能量**判定入侵
（`sense.zone_m` 距离门、`sense.energy_gate` 能量门、`min_frames` 连续帧确认）。

但产品需求是"**身后出现第二个人**"，需要数 `radar.frame` 里 `targets[]` 的**目标个数**。
LD2454 最多报 3 个目标，坐标齐全，完全够用。

### 有一个设计问题必须先确认，不要自己拍板

**雷达装在哪，决定了用户本人算不算一个目标：**

- 若雷达固定在显示器顶部**朝向身后过道**，用户在雷达背后 → 用户不在探测区
  → **1 个目标就是有人来了**
- 若雷达的探测范围也覆盖用户 → **2 个目标才是有人来了**

这两种情况阈值完全不同。**先问用户雷达的实际安装位置和朝向**，或者用真实数据确认
（人坐着不动时看 `targets[]` 长度是 0 还是 1）。

### 建议的实现方向

- 配置加 `sense.intruder_target_count`（默认值取决于上面的结论）
- 保留 `min_frames` 连续帧确认，避免单帧抖动误触发
- 保留 `cooldown_s` 冷却，避免反复切场景
- 用 Y 坐标（纵深）和速度判断"接近中"比单纯距离更准 —— 速度为负表示朝雷达靠近
- 现有的距离/能量门可以作为辅助条件保留，但不应是主判据

### 事件契约（不要改，上层依赖）

```
radar.frame     state, moving_cm, moving_energy, static_cm, static_energy,
                targets[]{x_mm, y_mm, speed_cms, dist_mm}, model
sense.intruder  distance_m, approaching(bool)
sense.clear     （无字段）
```
